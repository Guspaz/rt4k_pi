# Readme

*Disclaimer: This project was developed with the assistance of AI as of commit 036ab16.*

This project is intended to replace the rt4k_esp32 project after the manufacturer rugpulled me and downgraded the microcontroller after I bought my initial unit. It's a work-in-progress and is not yet fit for public consumption.

It's designed to run on the Raspberry Pi Zero 2 W (Pi02W), and only the Pi02W: the Zero 2 is the only model that has "unlimited" power output due to having a direct shunt between the USB power input and output, and we need the W version to be able to communicate with it over wifi. You connect the RT4K power supply to the Pi02W power input, and the RT4K itself to the other Pi02W USB port.

rt4k_pi communicates with the RT4K via the FTDI virtual serial port on the RT4K's USB power input, at 2,000,000 baud. It provides a web remote, live OSD mirroring, device status, and SD-card access through FUSE and an SMB share. These features require firmware supporting the corresponding text and RTL1 binary commands.

Incomplete installation instructions can be found at: https://github.com/Guspaz/rt4k_pi/blob/master/setup.md

The missing instructions are basically, use SSH/SCP to copy the rt4k_pi binary over to the /home/pi folder (assuming you used "pi" as the username) and run it, it will handle the rest of the install/config/setup itself.

## Building

The project targets .NET 10 and uses RazorSlices with minimal API endpoints. It publishes as a self-contained ARM64 Native AOT executable with embedded web assets. On a Linux ARM64 build machine with the .NET 10 SDK and Native AOT toolchain installed, run `dotnet publish -c Release -r linux-arm64`. The executable is `bin/Release/net10.0/linux-arm64/publish/rt4k_pi`.

Windows builds are useful for development, but FUSE, SMB setup, installation, and self-updating are Linux-specific. A Windows build does not validate deployment on the Pi.

## Serial TCP service

The optional ser2net service listens on port 2000 and is **text-command-only**, not a transparent binary serial bridge. It accepts CR-, LF-, or CRLF-terminated printable ASCII commands, up to 255 characters per command. Partial lines are retained until a terminator arrives; incomplete lines are discarded on disconnect.

Commands are serialized with web commands, status polls, OSD captures, and file transfers. Binary-mode commands (`get`, `put`, `sget`, `osd`, `osd2`, `font`, and `rtl1`) are rejected by both the TCP text interface and `/SendSerial`. Application-owned binary transfers continue to work. Ordinary TCP commands collect replies for one second; directory listings can wait up to 20 seconds for their terminator. `sha256` returns text and is supported with a 60-second response window. Once a command has been sent, cancellation waits for its reply window to finish before releasing serial ownership; a queued command can be canceled before it is sent.

Clients receive decoded text lines, including device text generated by other application activity, but not binary frames. Each client has an ordered output queue of 64 lines and a five-second write deadline; a full queue or stalled write closes the client. Invalid bytes and oversized command lines also close the connection. Disabling and re-enabling the service closes existing clients and starts a fresh listener.

## Settings and files

Settings are stored in `settings.json` beside the executable, loaded before services start, and saved using a flushed temporary file and atomic replacement. Existing property names are preserved. Display scales must be positive; model and version strings must not be empty.

Filesystem writes are staged in memory because the device only supports whole-file replacement:

- Staged files are limited to 64 MiB, including existing files being partially overwritten. Truncating a larger file to zero does not download its old contents.
- Retained staging buffers and read caches share a 128 MiB budget. This is not a total process-memory limit: transfers, temporary copies, the OSD, and the runtime need additional memory.
- Reads fall back to ranged transfers when a whole-file cache cannot fit. Staging that cannot fit returns an error rather than growing without a bound.
- Flush and fsync upload dirty contents and report transfer failures. Final release also attempts a pending upload. Failed uploads retain their dirty entry for a reopen/retry while the process remains running; pending data is not durable across a crash or shutdown.
- Unlink preserves pending changes if device deletion fails. Successfully unlinked open handles retain their buffered contents without recreating the deleted path. Unlinking an open, uncached file larger than the staging limit is rejected. Renaming over a tracked destination returns busy rather than discarding its state.

## Application updates

Only one update runs at a time. Downloads are streamed to a unique staging directory beside the executable, checked for HTTP success, size (at most 256 MiB), and SHA-256, then extracted and checked for a regular Linux ARM64 `rt4k_pi` executable. The executable is atomically replaced; other extracted files do not overwrite settings or the live installation.

The old binary is retained as `rt4k_pi.previous`. Installation errors after replacement attempt to restore it. If a new binary fails after restart, recovery is manual: stop the service, restore that previous binary as `rt4k_pi`, and restart the service. There is no automatic post-restart health check.
